# Informe técnico de seguridad — NeoTech ZGZ

**Fecha de corte:** 27 de noviembre de 2026  
**Alcance:** Vercel, GitHub, Supabase, Stripe y Cloudflare R2.  
**Método:** lectura de configuración y metadatos, consultas SQL de catálogo, análisis de workflows/migraciones, despliegues Preview y pruebas HTTP no destructivas desde un dispositivo remoto.  
**Limitación:** no es una auditoría de penetración independiente ni una certificación legal. No se han leído valores de secretos.

## Resumen ejecutivo

La web de producción está operativa y responde HTTP 200. La configuración de seguridad perimetral mejoró con una regla de rate limiting en modo bloqueo. No obstante, el sistema todavía no debe declararse completamente estabilizado: hay cambios de permisos de base de datos fusionados en GitHub pero pendientes de aplicar a producción, una credencial GitHub expuesta que sigue en el historial, falta CSP, no se ha demostrado una restauración completa y Vercel no permite activar OWASP Core Ruleset con el plan actual.

## Vercel

- Producción responde HTTP 200.
- Cabeceras verificadas: HSTS, X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy y Permissions-Policy.
- CSP ausente.
- SSO de Preview habilitado.
- Firewall activo.
- Regla personalizada de rate limiting: 100 solicitudes por IP/minuto, acción deny, aplicada a POST `/api/quotes`, POST `/api/contact` y GET `/api/quotes/lookup`.
- Bot Protection y AI Bots permanecen en modo log. La prueba de challenge desde curl devolvió 429; se revirtió a log para no arriesgar la disponibilidad sin validar navegador.
- OWASP Core Ruleset no disponible para el plan: Vercel respondió 402 payment_required.
- La API de Security Review devolvió 404; no hay informe de vulnerabilidades nativo verificable en esta sesión. Esto no equivale a cero vulnerabilidades.
- `npm audit --audit-level=high` y el build pasaron en los workflows de seguridad asociados a los PR revisados.

## Supabase

Proyectos examinados:
- Producción: `qkzmpxyefuqdhyxwfjcw`.
- Aislamiento/auditoría: `hdpikaqxeadqmckmmjfh`.

La producción mantiene RLS activo. `stripe_invoices` y `stripe_webhook_events` no tienen políticas RLS ni privilegios para `anon`/`authenticated`; permanecen cerradas intencionadamente y el acceso de escritura debe ser server-side.

El proyecto aislado tiene:
- INSERT en `support_tickets` limitado a `user_id`, `subject` y `message`.
- Una política SELECT owner-or-admin por tabla para `quotes`, `payments` y `support_tickets`.
- Pruebas de integración Auth/RLS en PostgreSQL/Supabase desechable.

Las dos migraciones se aplicaron individualmente en producción después de validarlas en Preview. El advisor ya no informa `multiple_permissive_policies` y los INSERT de tickets están limitados a tres columnas. No ejecutar `supabase db push` global: los prefijos de versión del repositorio no coinciden completamente con las versiones aplicadas en producción y Preview tiene una historia independiente. PR #88 separa las migraciones Preview/test-only del directorio de producción.

## Acciones necesarias para cerrar

1. Revocar el PAT comprometido y planificar reescritura de historial con aviso a colaboradores.
2. Mantener monitorización posterior de RLS y reconciliar las versiones del historial antes de cualquier migración automatizada.
3. Habilitar leaked password protection en Supabase Auth.
4. Diseñar CSP con nonce y validar el comportamiento en navegador.
5. Definir residencia EU y retención para R2; configurar credenciales bucket-scoped.
6. Ejecutar backup cifrado y restauración completa PostgreSQL 17 en destino desechable.
7. Completar pruebas Stripe TEST; mantener checkout live desactivado.
8. Validar React 19 con pruebas de navegador antes de fusionar/promover.
9. Reconciliar versiones de migraciones por entorno antes de permitir cualquier `db push`.

**Criterio de cierre:** no marcar como resuelto ningún control hasta que exista evidencia observable en el entorno al que aplica.
